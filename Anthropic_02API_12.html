② キーポイント
  • 1
    Claudeモデル3種の使い分け
    Haiku 速度・低コスト・大量処理（推論機能なし）  Sonnet バランス重視・コーディング得意・実用的なほとんどのケース  Opus 複雑な多段階タスク・深い推論・高コスト許容の場面。 1つのアプリ内でタスクごとに使い分けるのが現実的なアプローチ。
  • 2
    APIはステートレス — 全履歴を毎回送る
    Anthropic API はリクエスト間でメッセージを保存しない。マルチターン会話を実現するには 過去の全メッセージをコードで管理し、毎回まとめて送信する必要がある。
    client.messages.create( model="claude-sonnet-4-6", max_tokens=1000, messages=[ {"role": "user", "content": "最初の質問"}, {"role": "assistant", "content": "最初の回答"}, {"role": "user", "content": "続きの質問"}, # 全履歴を毎回送る ] )
  • 3
    プロンプトエンジニアリング4技法
    ①明確な動詞で始める（"Generate a one-day meal plan…"） ②属性/手順ガイドラインを追加（出力フォーマット・考慮すべき手順） ③XMLタグで構造化（<athlete_info> 等で入力データを明示） ④例示を追加（one-shot / multi-shot）
    ✅ 4つを組み合わせることでスコアが 2.32 → 7.86 に改善した実例あり。プロンプト評価パイプライン（データセット生成 → LLM実行 → モデルベース採点）で客観的に計測すること。
  • 4
    ツール使用のループ構造
    ツールスキーマを渡す → Claude が tool_use ブロックで呼び出し要求 → サーバーが実行 → tool_result を返す → 繰り返し。 stop_reason == "tool_use" の間ループを続け、そうでなければ終了。
    while True: response = chat(messages, tools=tools) messages.append(response) if response.stop_reason != "tool_use": break tool_results = run_tools(response) # tool_use ブロックを実行 messages.append({"role": "user", "content": tool_results})
    ℹ️ Batch Tool パターンを使うと、Claude が複数ツールを1リクエストで並列呼び出しできる。逐次呼び出しの往復を削減。
  • 5
    RAGパイプライン — 大規模文書の活用
    ① チャンキング（サイズ/構造/セマンティック）→ ② 埋め込み生成（Voyage AI）→ ③ ベクトルDB保存 → ④ クエリ変換 → ⑤ ハイブリッド検索（セマンティック + BM25） → ⑥ Reciprocal Rank Fusion で統合 → ⑦ Reranking（LLM）→ ⑧ プロンプト組み立て。
    ℹ️ Contextual Retrieval: チャンクを埋め込む前に LLM で文書全体のコンテキストを付加すると検索精度が大幅に向上する。
  • 6
    MCPの本質 — ツール実装負担をオフロード
    MCP（Model Context Protocol）は Claude とサービスをつなぐ標準プロトコル。 サーバー側が Tools（アクション）・Resources（データ）・Prompts（テンプレート） を提供し、 開発者はツールスキーマの実装から解放される。Claude Code 自体もMCPクライアントとして動作し、 claude mcp add コマンドで任意のサーバーを接続できる。
  • 7
    エージェント vs ワークフロー — 信頼性を優先
    ワークフロー：手順が明確なタスク向け。高信頼性・テスト容易・完了率が高い。 チェーン / 並列化 / ルーティング / 評価-最適化の4パターンがある。
    エージェント：手順が不明なタスク向け。柔軟だが完了率が低下する。
    ⚠️ エージェントは便利に見えるが完了率が下がる。まずワークフローで解決できないかを検討すること。「ユーザーは100%動くプロダクトを求めている」

④ 用語集（初心者向け解説）
トークン
文章を分割した最小単位。英語1単語≈1トークン、日本語は1〜2文字。APIの料金はトークン数で決まる。
エンベディング
テキストの「意味」を-1〜+1の数値リストで表したもの。意味が近い文章ほど数値が近くなるため、RAGの類似検索に使う。
RAG
大きな文書から質問に関係する部分だけを取り出してClaudeに渡す技術。コンテキスト長の制限問題を解決する。
MCP
Model Context Protocol。ClaudeとサービスをつなぐためのAPI仕様。サービス側がツールを定義するため開発者の実装コストが下がる。
プロンプトキャッシュ
同じ入力を再利用するとき前回の計算結果を再使用してコスト削減・高速化する仕組み。最長1時間有効。最低1024トークン必要。
ストップシーケンス
Claudeの生成を止めるトリガー文字列。特定のテキストが出た瞬間に生成が止まる。構造化データ取得に便利。
ツールスキーマ
Claudeに「どんなツールが使えるか」を教えるJSON定義。関数名・説明・引数の型と説明を記載する。
アシスタントプリフィル
会話の最後にアシスタントメッセージを手動で追加してClaudeの回答方向を誘導する技法。構造化データ出力に効果的。
⑤ 理解度チェック
Q1
Claudeの3つのモデルファミリー（Haiku・Sonnet・Opus）の強みと最適な使用場面を答えてください。
答えを見る
Haiku：最速・最低コスト。推論機能なし。リアルタイム対話・高ボリューム処理・シンプルなタスクに最適。
Sonnet：知性・速度・コストのバランスが良く、コーディング能力が高い。実用的なほとんどのユースケースに推奨。
Opus：最高知性。複雑な多段階タスクや深い推論が必要な場面向け。コスト・レイテンシが高いのがトレードオフ。
実際のアプリでは1種類に絞らず、タスクの性質に応じて複数モデルを使い分けるのが現実的。
Q2
RAGパイプラインで「ハイブリッド検索」が推奨される理由を、セマンティック検索とBM25それぞれの弱点をふまえて説明してください。
答えを見る
セマンティック検索の弱点：意味的な類似度で検索するため、特定の専門用語や固有名詞の完全一致を見逃すことがある。
BM25の弱点：キーワードの出現頻度に依存するため、言い回しが変わると見つけられない。
ハイブリッド検索：両者の結果をReciprocal Rank Fusionで統合することで、意味的な近さと用語の一致を両立できる。「ENGチーム」と「エンジニアリングチーム」のような表記ゆれにも対応可能になる。
Q3
エージェントよりワークフローを優先すべき理由と、エージェントを選択すべき場面の判断基準を説明してください。
答えを見る
ワークフロー優先の理由：手順が固定されているためテストしやすく、タスク完了率が高い。ユーザーは高機能より「確実に動く」ことを求めている。
エージェントを選ぶ判断基準：タスクの実行手順が事前に特定できないとき。エージェントは提供したツールを組み合わせて動的に問題を解決できるが、完了率は低下する。
原則：まずワークフローで解決できないかを検討し、どうしても手順が予測できない場合のみエージェントを採用する。
