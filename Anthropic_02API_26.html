① 一言まとめ
レクチャー25 でハードコードしていた score=10 を、本物の Grader（採点者） に置き換える。 Code / Model / Human の 3種類 から選び、今回は Model Based Grading（モデル採点）を実装。
ポイントは「スコアだけ要求せず strengths / weaknesses / reasoning / score の4点セット」で書かせること。 これでスコアが middling な値（5や6） に偏るのを防ぎ、v1 と v2 のプロンプトを 客観数値で比較 できる baseline が完成する。

③ 採点者3種比較
種類 方式 得意 苦手 使う場面
Code プログラム的チェック 長さ・syntax・キーワード有無 「品質」「ニュアンス」 形式 / 構文の機械検証
Model 別 API コールで Claude が採点 応答品質 / 指示追従 / 完全性 不安定（同入力で別スコア） 柔軟な品質判定（baseline）
Human 人がレビュー 全体的応答の質 / 深さ / 関連性 遅い・人件費・大量処理不可 重要判断の最終確認
実運用パターン: Code（速・形式チェック）+ Model（baseline）+ Human（重要判断）の 3層運用。次レクチャーで Code Grader（プログラム検証）を学んでハイブリッド採点へ進化。
④ 評価基準の定義（3軸）
基準 内容 担当する Grader
Format 形式的な制約。例: Python / JSON / regex のみ返し、説明なし Code Grader
Valid Syntax 有効な構文。Python パース・JSON パース・regex compile が成功するか Code Grader
Task Following タスクの意図に沿っているか / 正確で実用的か Model Grader
役割分担:「コードでチェックできるもの（Format / Valid Syntax）は Code で安価高速に」「柔軟性が必要なもの（Task Following）は Model で」。
これがハイブリッド採点の設計原則。今回は Model Grader 実装が中心、次レクチャーで Code Grader と組み合わせる。

⑥ 理解度チェック
Q1
Model Grader プロンプトに「score だけ書いて」と要求すると、なぜダメなのですか？対処法は？
答えを見る
ダメな理由: Claude は深く考えずに「無難な中間値（5や6）」に偏る。極端な値（1や10）を避ける傾向があるため、v1 と v2 のスコア差が出ず評価が機能しない。
対処法: strengths / weaknesses / reasoning / score の 4点セット を書かせる。reasoning を先に書く順序にすると、Claude が出力を真剣に分析してから採点する流れになり、差別化されたスコアが出る。Chain of Thought プロンプトテクニックの応用。
Q2
3つの評価基準（Format / Valid Syntax / Task Following）はそれぞれどの Grader が担当すべき？理由は？
答えを見る
Format / Valid Syntax → Code Grader: 「Python / JSON / regex 形式である」「パースが通る」は プログラムで決定論的に判定可能。Code Grader なら速・安・確実。
Task Following → Model Grader: 「タスクの意図に合っているか」「実用的か」はコードでは判定不能。柔軟な品質評価には Model Grader が必要。
役割分担の原則: 「コードで判定可能なものはコードで」「柔軟性が必要なものはモデルで」。次レクチャーで両者を組み合わせるハイブリッド採点に進化。
Q3
Model Grader のクリーンな JSON 出力を確保するためのテクニックは？
答えを見る
pre-fill + stop sequence の組み合わせ。
① assistant message に ```json を pre-fill（Claude は「すでに開始した」と認識）
② stop sequence に ``` を指定（Claude が閉じバッククォートを出した瞬間に停止）

これは Structured Data 生成（レクチャー20-21）と同じテクニックの応用。
