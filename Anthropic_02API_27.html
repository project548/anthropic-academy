① 一言まとめ
コードを生成するAIを評価する時、応答が「理にかなっているか」だけでなく、有効な構文・正しい形式 を **プログラム的に検証** する仕組みが Code Based Grading。
validate_python / validate_json / validate_regex の3関数で構文チェック → Model Grader（品質）+ Code Grader（構文）の 平均 で最終スコア。これでハイブリッド採点が完成し、「構文OK + 内容OK」の両立を客観数値で測れるようになる。
② キーポイント
  • 1
    3つの評価基準: Format / Valid Syntax / Task Following
    ① Format（説明なしのコードのみ返すか）/ ② Valid Syntax（構文として解析可能か）→ Code Grader 担当
    ③ Task Following（タスク内容に正確に答えているか）→ Model Grader 担当
    この3軸を合わせて 包括的な評価 が実現する。
  • 2
    3つの構文検証関数（validator）
    それぞれの形式に従ってテキストを解析を試み、成功なら 10 / 失敗なら 0 を返す。
    def validate_json(text): try: json.loads(text.strip()) return 10 except json.JSONDecodeError: return 0 def validate_python(text): try: ast.parse(text.strip()) return 10 except SyntaxError: return 0 def validate_regex(text): try: re.compile(text.strip()) return 10 except re.error: return 0
  • 3
    データセットに「format」キーを追加
    Code Grader が どのバリデーターを使うか 判断できるよう、テストケースに format フィールドを追加。generate_dataset() のサンプル出力構造にも反映。
    { "task": "Create a Python function to validate an AWS IAM username", "format": "python" }
  • 4
    プロンプトの明確性 + Pre-fill で「raw コードのみ」
    プロンプトに「コードのみ・説明なし」と明示 + assistant pre-fill で ```code を入れて Claude にコード生成を促す。
    * Respond only with Python, JSON, or a plain Regex * Do not add any comments or commentary or explanation add_assistant_message(messages, "```code")
    ポイント: ```code という汎用 pre-fill を使うことで、format が Python/JSON/Regex のどれでも事前指定不要で動く。
  • 5
    スコアの組み合わせ = 平均値（ハイブリッド採点）
    (model_score + syntax_score) / 2 を最終スコアに。コンテンツの質と技術的正確さを 同等の重み付け。重みは用途で調整可。
    model_grade = grade_by_model(test_case, output) model_score = model_grade["score"] syntax_score = grade_syntax(output, test_case) score = (model_score + syntax_score) / 2
  • 6
    スコア絶対値より「改善幅」を見る
    スコア自体に良し悪しはない。重要なのは プロンプト改善でスコアが向上するか。 主観評価から脱却して、プロンプト設計の進捗を 定量的に測定 できる状態が完成。
    v1 (6.5) → v2 (8.2) のように 差分（+1.7） がプロンプト改善の客観的な証拠になる。
  • 7
    なぜハイブリッドが勝つか
    Model 単独: 構文を厳密チェックしない → 「動きそう」雰囲気判定 / スコア不安定
    Code 単独: 「構文OK だが意味が違う」コードを満点にしてしまう / 空関数も10点
    両者を組み合わせる: Code が構文を保証 + Model が意味を評価 → 「片方だけOK」を排除
    制約: format が事前定義できないタスク（自由文章生成等）には Code Grader 使えない → Model 単独で対応
③ 構文検証関数 詳細
関数 使用ライブラリ 成功条件 失敗時例外
validate_python ast.parse() Python 構文として解析可能 SyntaxError
validate_json json.loads() JSON文字列として解析可能 JSONDecodeError
validate_regex re.compile() 正規表現として compile 可能 re.error
共通実装パターン: text.strip() で前後空白除去 → try/except でパース試行 → 成功 return 10 / 失敗 return 0。
ast.parse は構文のみチェック（実行はしない）ので、不審なコードを評価しても安全。
④ ハイブリッド採点 動作例
ケース model_score syntax_score final score 意味
品質高 + 構文OK 9 10 9.5 理想形 ✨
品質高 + 構文NG 9 0 4.5 動かないので大幅減点
品質微妙 + 構文OK 6 10 8 構文OKでスコア底上げ
品質微妙 + 構文NG 4 0 2 両方ダメ → 最低スコア
重み付けは用途次第: 構文重視なら 0.7 × syntax + 0.3 × model、品質重視なら逆。デフォルトは 50:50。

⑥ 理解度チェック
Q1
3つの評価基準（Format / Valid Syntax / Task Following）はそれぞれどの Grader が担当？
答えを見る
Format → Code Grader: 「Python/JSON/Regex のみ・説明なし」かを機械的に判定
Valid Syntax → Code Grader: ast.parse / json.loads / re.compile でパース成功するか判定
Task Following → Model Grader: 「タスク内容に正確に答えているか」を Claude に評価させる
役割分担の原則: 「コードで判定可能なもの = Code」「柔軟性が必要なもの = Model」。両者の平均で最終スコア。
Q2
なぜプロンプトに add_assistant_message(messages, "```code") という汎用 pre-fill を使うのですか？
答えを見る
format ごとに pre-fill を分岐させると複雑: Python なら ```python、JSON なら ```json と切り替える必要がある。
解決策: ```code という 汎用ラベル を使えば、Claude は「とにかくコードブロックを開始する」と理解 → format に関わらず説明なしの raw コードを返す。
stop sequence の ``` でコードブロック終了を検知 → 余計な後付けテキストも除外できる。
Q3
「スコア絶対値に良し悪しはない」とはどういう意味？評価ワークフローの本質は？
答えを見る
絶対値の意味のなさ: 「平均6.5」が良いか悪いかは、タスクの難易度・データセットの構成によって変わる → 単独では判断できない。
本質 = 改善幅（差分）: プロンプト v1 で 6.5 → v2 で 8.2 という +1.7 の改善 が客観的な進捗の証拠。
これにより、主観評価（「なんとなく良くなった」）から脱却 し、プロンプト設計を 定量的に測定 できる状態が完成。
Code Based Grading 単独ではなく、これを使って イテレーションを回すこと が真の目的。
