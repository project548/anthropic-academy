Sending tool results— tool 実行結果を Claude に返してワークフロー完結

Anthropic Academy / コース02 Claude with the Anthropic API

① tool_result を返す — 最後の一手

#41 で受け取った tool_use ブロックの中身に従って関数を実行し、その 結果を Claude に返す ことで、tool use の完全な往復が成立する。

これで「Claude が道具を要請 → サーバーが実行 → Claude が結果を読んで自然言語応答」の 完全フロー が完成する。

② 関数を実行する

# Claude が要求した引数(辞書)
args = response.content[1].input
# → { "date_format": "%H:%M:%S" }

# Python の ** で辞書を展開してキーワード引数として渡す
result = get_current_datetime(**args)
# → "15:04:22"

** は Python の 辞書アンパック。{"a": 1, "b": 2} を a=1, b=2 として展開する。Claude が JSON で渡してきた引数をそのまま関数に渡せる。

③ tool_result ブロックの3項目

キー内容例
tool_use_id対応する tool_use ブロックの id を必ず一致させる"toolu_01ABC..."
content関数の戻り値を文字列にして入れる"15:04:22"
is_errorエラー時 True(成功時 False)False
tool_use_id の照合が最重要。複数 tool 並列要請のとき、ID が一致していないと Claude は「どの結果がどの要請に対応するか」分からなくなる。

④ 続きのリクエストを組み立てる

messages.append({
    "role": "user",  # ← tool_result は user メッセージとして送る
    "content": [{
        "type": "tool_result",
        "tool_use_id": response.content[1].id,
        "content": "15:04:22",
        "is_error": False
    }]
})
  • role は "user"(assistant ではない・ここ要注意)
  • content は 配列(複数 tool_result を入れられる)
  • 元の user / assistant メッセージはそのまま残し、append する
なぜ role が user? Claude の視点では「ツール実行結果は、ユーザー側(サーバー側)から渡される情報」だから。Claude 自身は道具を持っていないので、結果は外部(=user 側)から来る扱い。

⑤ 最終リクエストでも tools を渡す

client.messages.create(
    model=model,
    max_tokens=1000,
    messages=messages,
    tools=[get_current_datetime_schema]  # ← 二度目の呼び出しでも必須
)
Why? 会話履歴に tool_use / tool_result が含まれているので、Claude がそれを解釈するために スキーマ情報が引き続き必要。tools 引数を省略すると Claude は履歴を読めなくなる。

⑥ 複数 tool 呼び出しの扱い

Claude は 1回の返答で複数のツールを並列要請 することもある。例: 「10+10 と 30+30 は?」 → tool_use ブロック2つ。

図① 複数 tool_use 並列要請 → ID で照合して並列 tool_result を返す

ID を必ず照合 して、対応する tool_result を返す。順番がずれても ID で紐付けされる設計。

⑦ tool use 完全フロー(再掲・コード付き)

# [1] user 質問 + tools=スキーマ
messages = [{"role": "user", "content": "今何時?"}]
response = client.messages.create(
    model=model, max_tokens=1000, messages=messages,
    tools=[get_current_datetime_schema])

# [2] assistant (text + tool_use) を履歴に保存
messages.append({"role": "assistant", "content": response.content})

# [3] サーバーが関数実行
tool_use = response.content[1]  # tool_use block
result = get_current_datetime(**tool_use.input)

# [4] user (tool_result) + tools=スキーマ
messages.append({
    "role": "user",
    "content": [{
        "type": "tool_result",
        "tool_use_id": tool_use.id,
        "content": str(result),
        "is_error": False
    }]
})
final = client.messages.create(
    model=model, max_tokens=1000, messages=messages,
    tools=[get_current_datetime_schema])

# [5] assistant 最終応答(自然言語)
print(final.content[0].text)  # → "現在は 15:04:22 です"

⑪ 理解度チェック

Q1. tool_result ブロックの3項目は?

① tool_use_id(対応する tool_use の id と一致)
② content(関数の戻り値を文字列化)
③ is_error(エラー時 True)

Q2. なぜ tool_result の role は "user" なの?

Claude の視点では「ツール実行結果は、ユーザー側(サーバー側)から渡される情報」だから。Claude 自身は道具を持っていないので、結果は外部(=user 側)から来る扱いになる。

Q3. 最終リクエストで tools 引数を省略するとどうなる?

会話履歴に tool_use / tool_result が含まれているのに、Claude がそれを解釈するためのスキーマがない状態になる。結果、Claude は履歴を読めず、エラーまたは破綻した応答を返す。tools 引数は最後まで必ず渡す。

Q4. 複数 tool 並列要請のとき、どう対応すれば良い?

tool_use ブロックそれぞれの id を取り出し、対応する tool_result を 同じ ID で 返す。content 配列に複数の tool_result を入れて1回の user メッセージで送る。順番ではなく ID で紐付けされる設計。
