① 一言まとめ
Claude で良いプロンプトを書くだけでは不十分。prompt engineering（書き方を改善する技術）と prompt evaluation（自動テストで効果を測定する仕組み）の両輪が必要。本番投入前に evaluation pipeline で客観的スコアを出して反復改善するのが、信頼性の高い AI アプリの王道。
② キーポイント
  • 1
    Prompt Engineering と Prompt Evaluation は別物・補完関係
    Prompt Engineering = 書き方の技術（multishot prompting、XML tags 構造化など）。Claude にどう伝えるかを工夫する。
    Prompt Evaluation = 自動テストで「実際にうまく動くか」を測る。プロンプトの効果を客観的に検証する。
  • 2
    プロンプトを書いた後の3つの選択肢
    Option 1: 1〜2回テストしてOKと判断 → 本番投入。**production で壊れるリスク大**
    Option 2: 数回テストして corner case を1〜2個対応 → 想定外入力で破綻しがち
    Option 3: evaluation pipeline で点数化 → 客観的指標で iterate（推奨）
  • 3
    なぜ大半のエンジニアが Option 1/2 の罠にハマるか
    真面目なアプリなのに、十分テストしないまま本番投入してしまうのはよくある罠。実ユーザーが想定外の使い方をする量を過小評価するから。limited testing で通った prompt も、real-world inputs では崩れる。
  • 4
    Evaluation-First Approach（評価優先アプローチ）
    Option 3 = systematic approach。evaluation pipeline で objective metrics を取得し、data-driven に改善ループを回す。
    ✅ Identify weaknesses before they become production issues
    ✅ Compare different prompt versions objectively
    ✅ Iterate with confidence based on measurable improvements
    ✅ Build more reliable AI applications
  • 5
    投資対効果：先行投資 vs 信頼性
    Evaluation pipeline は **upfront investment**（時間・テストインフラ）がかかるが、最終アプリの **reliability and robustness** で確実に元が取れる。「ユーザーに見つかってから直す」より「開発中に潰す」が圧倒的に安い。
③ 3つの選択肢比較
項目 Option 1: 1回テストして本番 Option 2: 数回テスト + corner case 対応 Option 3: evaluation pipeline
テスト回数 1〜2回 数回 + 個別 corner case 多数（評価データセット全件）
客観性 主観のみ 主観 + 一部データ objective metrics（数値スコア）
本番リスク ★★★ 高（壊れがち） ★★ 中（想定外で崩れる） ★ 低（事前に潰せる）
必要工数 少ない 普通 多い（pipeline 構築）
適した用途 使い捨て・実験スクリプト 個人プロジェクト・PoC 本番アプリ・信頼性重視
iterate の根拠 勘・気分 気付いた問題の都度修正 measurable improvements
本番運用なら必ず Option 3。 Option 1/2 は trap。real users は想定外の入力をしてくる。
④ 用語集（演習で覚える主要キーワード）
prompt engineering
プロンプトを「より効果的に書く」ための技術群。multishot prompting、XML tags 構造化、Being Specific などの best practices。
prompt evaluation
プロンプトの効果を「自動テストで測る」アプローチ。expected answers との比較、版違い対比、エラー発見など。
evaluation pipeline
テストデータセット → プロンプト実行 → 採点 → 集計 → iterate を自動化した仕組み。data-driven 改善の基盤。
multishot prompting
プロンプトに複数の入出力例（few-shot examples）を含める手法。Claude に期待する形式・品質を学ばせる。
corner case
通常の使い方では出ないが、現実には起こる例外的な入力やシナリオ。limited testing では見落とされがち。
objective metrics
主観ではなく数値で測れる客観指標（例: 1〜10スコア、成功率、JSON parse 成功率）。比較・改善の根拠になる。
⑤ 理解度チェック
Q1
prompt engineering と prompt evaluation の違いを一言で説明してください。
答えを見る
prompt engineering = プロンプトの **書き方** の技術（HOW to write）。multishot や XML tags など、Claude が理解しやすくする技法。
prompt evaluation = プロンプトの **効果測定** の仕組み（HOW WELL it works）。自動テストで客観スコアを出す。両者は補完関係で、本番品質には両方必要。
Q2
「書いたプロンプトを2〜3回テストしてOKだから本番に出す」アプローチの最大のリスクは？
答えを見る
real users が想定外の入力（corner case / unexpected inputs）を大量に投げてくるため、**limited testing で通った prompt が production で壊れる**。エンジニアは edge case の量を過小評価しがち。Option 1 は最もリスクが高く、Option 2 ですらまだ甘い。
Q3
evaluation pipeline を使うと何が得られますか？4つ挙げてください。
答えを見る
① Identify weaknesses before they become production issues（弱点を本番障害になる前に発見）
② Compare different prompt versions objectively（プロンプト版違いを客観比較）
③ Iterate with confidence based on measurable improvements（測定可能な改善で自信を持って反復）
④ Build more reliable AI applications（信頼性の高い AI アプリ構築）
