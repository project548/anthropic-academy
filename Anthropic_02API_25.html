③ 3関数詳細
関数 責務 入力 出力
run_prompt 1テストケースをプロンプトとマージ → Claude 送信 test_case (dict) Claude の output (str)
run_test_case run_prompt 呼び出し + 採点（現状ハードコード10） test_case (dict) {output, test_case, score}

⑤ 理解度チェック
Q1
eval pipeline の3関数（run_prompt / run_test_case / run_eval）はそれぞれ何の責務を持っていますか？
答えを見る
run_prompt = 1テストケースをプロンプトテンプレートとマージし、Claude に送信して output を返す（実際のAPI呼び出し）
run_test_case = run_prompt を呼び、結果を採点して { output, test_case, score } の構造化辞書を返す（オーケストレーション + 採点）
run_eval = データセット全体をループし、各 test_case に run_test_case を適用して results を蓄積する（バッチ実行）
責務分離により、改善ポイント（プロンプト改善 / 採点改善 / 並列化）がそれぞれ別関数で対応可能。
Q2
なぜ score を 10 でハードコードしているのですか？このまま放置するとどんな問題がありますか？
答えを見る
理由: パイプラインの骨格を先に完成させ、grader 実装を別ステップに分離するため。「TODO - Grading」コメントで次の作業を明示している。
放置すると: ① 全テストケースで score=10 になる → プロンプト v1 と v2 を 比較できない / ② 「改善した気がする」という主観判定に戻る / ③ そもそも eval パイプラインの目的（客観スコア）を達成できない。
次レクチャーで grader を実装してハードコード10を本物のスコアに置き換えることが必須。
Q3
run_prompt のプロンプトはあえてシンプル（フォーマット指示なし）。これによってどんな問題が起き、どう活用できますか？
答えを見る
起きる問題: Claude が冗長な説明・前置き・余計な解説を含めて出力する → output が綺麗な構造化データではなくなる。
活用方法: ① これは「プロンプト改良の出発点」として意図的に粗いまま残す / ② grader 実装後に「v1 (シンプル) vs v2 (フォーマット指示追加)」のスコア差を 客観数値で確認できる / ③ baseline スコアが「どこから出発したか」を後から振り返れる。
シンプルなまま走らせて改善余地を可視化することが、評価ワークフローの本質。
