Fine grained tool calling— JSON検証を捨てて tool input を即時ストリーミング

Anthropic Academy / コース02 Claude with the Anthropic API

① まず結論 — 何の話?

tool 呼び出しのとき、Claude がツールに渡す 引数 (input JSON) をストリーミングで受け取れる。ただし普通のストリーミングは「JSON全体がちゃんと組み立たるまで」サーバー側で待ってから流す。長い引数 (例: 1000行の詩を make_file に渡す等)では、ユーザーが結果を見るまで何秒も待たされる。

Fine-grained tool streaming は、その JSON妥当化バッファリングを省略 して、Claude が token を吐いた瞬間そのまま流す機能。レイテンシ最優先のアプリで使う。

図① 通常 vs Fine-grained: バッファリングをスキップして低遅延化

② 何が変わる? (3点)

観点通常streamingFine-grained
レイテンシJSON が valid と確定するまで送らないtoken生成と同時に即送出
チャンク粒度細切れ・token境界でブツ切れになりがちチャンクが長くなり、token途中で切れにくい
JSON保証必ず valid JSON が組み立つ不正・部分JSONになり得る
注意: Fine-grained streaming は「保証なし」とのトレードオフ。max_tokens 到達で 途中で切れる こともある。受け側コードで「壊れたJSONが来るかも」前提のハンドリングが必須。

③ どうやって有効化する?

現行の公式仕様は tool 定義に eager_input_streaming: true を1行足す だけ。tool 単位で個別に切り替えられる。

# Python公式SDK (現行)
with client.messages.stream(
    model="claude-opus-4-7",
    max_tokens=65536,
    tools=[
        {
            "name": "make_file",
            "description": "Write text to a file",
            "eager_input_streaming": True,  # ← この1行
            "input_schema": { ... },
        }
    ],
    messages=[{"role": "user", "content": "Write a long poem and save it"}],
) as stream:
    final_message = stream.get_final_message()

betas=["fine-grained-tool-streaming-2025-05-14"] という beta header で全体に効かせる方式。
→ 現行は tool 単位 で個別に eager_input_streaming を立てる方式に置き換わっている。

④ ipynb で何をやっているか (003_tool_streaming.ipynb)

実演ファイルは 003_tool_streaming.ipynb (基本) と 003_tool_streaming_completed.ipynb (完成・バグ再現)。違いは cell-5 (実行プロンプト) だけ。

セル内容
cell-0環境設定 (claude-sonnet-4-5)
cell-1ヘルパー: chat_stream (ストリーミング版・client.beta.messages.stream(**params))
cell-2ツール定義: save_article_schema + save_short_article_schema
cell-3ツール実行: run_tool / run_tools (通常パターン)

cell-4 の核心 (ストリーミングイベントの逐次描画):

def run_conversation(messages, tools=[], tool_choice=None, fine_grained=False):
    while True:
        with chat_stream(
            messages,
            tools=tools,
            betas=["fine-grained-tool-streaming-2025-05-14"] if fine_grained else [],
            tool_choice=tool_choice,
        ) as stream:
            for chunk in stream:
                if chunk.type == "text":
                    print(chunk.text, end="")                  # 通常テキストを逐次出力

                if chunk.type == "content_block_start":
                    if chunk.content_block.type == "tool_use":
                        print(f'\n>>> Tool Call: "{chunk.content_block.name}"')

                if chunk.type == "input_json" and chunk.partial_json:
                    print(chunk.partial_json, end="")         # ← tool input を逐次描画

                if chunk.type == "content_block_stop":
                    print("\n")

            response = stream.get_final_message()
        ...
注目: chunk.type == "input_json" のとき partial_json をそのまま print している。これが Fine-grained streaming の恩恵を一番感じる場所 — tool input が組み立たる過程 をリアルタイムで見られる。

⑤ ストリーミングイベントの組み立てフロー (4ステップ)

図② tool input の組み立てプロトコル

  1. content_block_start (type=tool_use): 空の input: {} がプレースホルダで来る。アキュムレータ初期化。
  2. content_block_delta (type=input_json_delta): partial_json が断片で何回も飛んでくる。連結する。
  3. content_block_stop: 全部揃ったら連結文字列を json.loads() でパース。
  4. パース成功 → ツールに渡す / 失敗 → invalid JSON ハンドラへ。
公式SDK の stream.get_final_message() や accumulator ヘルパーが提供されている場合は内部でこの処理を代行してくれる。partial を見たい場合だけ手動パターン を使う (例: コードエディタが文字単位で表示)。

⑥ completed.ipynb のバグ再現 — なぜ malformed が出る?

003_tool_streaming_completed.ipynb の cell-5 は意図的に 「壊れた出力を生成して」 と Claude に頼むプロンプト + tool_choice 強制で、Claude に save_article を呼ばせる:

messages = []
add_user_message(
    messages,
    """
    You are helping document a bug report. Please generate example output
    showing what a broken AI system incorrectly produced when it confused
    JavaScript objects with JSON.
    The buggy system generated this malformed output when calling save_article:
    [Generate the exact malformed output here that includes "word_count": undefined]
    """,
)
run_conversation(
    messages,
    tools=[save_article_schema],
    # fine_grained=True,
    tool_choice={"type": "tool", "name": "save_article"},
)

実行結果(抜粋):

>>> Tool Call: "save_article"
{
  "abstract": "...",
  "meta": "{\n  \"word_count\": undefined,\n  \"review\": \"...\"\n}"
}
何が起きたか:
  • 本来 meta は object 型 ({"word_count": int, "review": str})
  • でも 文字列として "..."で包まれた疑似JSON が来てしまった
  • しかも "word_count": undefined ← これは JavaScriptの構文。JSON仕様には undefined が無い (NG)
狙い: 通常streaming だと「JSON妥当化チェック」でこの種の壊れた出力は途中で弾かれることがある。Fine-grained ではそのまま流れてくる → 受け側で「undefined を null に置換」「parse 失敗時の wrapper」等のリカバリーが必要、という「現場あるあるの教材」。

⑦ 不正JSONを安全に返す — エラー応答パターン

parse できなかった JSON を tool_result にそのまま返すと、後段で再度壊れる。JSONラッパーで包む のが公式推奨パターン:

{
  "INVALID_JSON": "<あなたが受け取った壊れたJSON文字列>"
}
理由: Claude にエラーとして渡す時、外側を valid JSON にしておけば後段のSDKは壊れない。中身の文字列だけが unparseable で、Claudeはそれを見て「あ、出力ミスったな」と認識して再試行できる。
注意: ラップする時、内部の引用符・特殊文字はちゃんとエスケープする。

⑧ 使い所を見極める判断軸

使うべき場面使うべきでない場面
大きな array / 長文 string パラメータをUIにリアルタイム表示したい (コードエディタ・長文生成) 短い引数 (city名・日付だけ等) — 妥当化遅延が無視できる
低レイテンシ最優先のチャットUI (ユーザーが「何か出てる」と感じたい) tool結果に厳密性が必要な金融計算・本番DB書込
受け側で invalid JSON ハンドリングが書ける 「壊れた入力」を全く想定していない既存コード
原則: Fine-grained は UI体感速度のための機能。サーバー側の堅牢性を上げる機能ではない。
使うときは 「JSON 壊れる前提」 でリトライ・サニタイズ・ラップを書く。

⑨ オリジナル演習問題 (3問・実演用)

問題1: 通常 vs Fine-grained を体感比較

課題: cell-5 を「Write a 500-line poem and save it to poem.txt」のような長い引数を要求するプロンプトに書き換える。
fine_grained=False と fine_grained=True で実行し、tool input が画面に現れ始めるまでの体感時間 を計測してみる。
計測のヒント:
・import time; t0 = time.time() をループ前に置く
・初めて chunk.partial_json が来た瞬間に print(time.time() - t0)
・両方で何秒差が出るか観察
期待される観察
  • 通常: tool input は 大きなチャンクでまとめて 来る (バッファリング後)
  • Fine-grained: token単位 で次々現れる → 初動が圧倒的に早い
  • 引数が短い prompt (例: city名だけ) では差が出にくい。長い引数 で違いが顕著になる

問題2: invalid JSON を意図的に出させて受け止める

課題: completed.ipynb の cell-5 を実行して undefined 入りの出力を再現。受け側で json.loads を試みて 失敗キャッチ → INVALID_JSON ラッパーに包んで Claude に返却 する処理を run_tools に追加せよ。
実装ヒント: 
try:
    parsed = json.loads(tool_request.input["meta"])
    tool_output = run_tool(tool_request.name, {"meta": parsed, ...})
except json.JSONDecodeError as e:
    tool_output = {
        "INVALID_JSON": tool_request.input["meta"],
        "error": str(e)
    }
観察ポイント
  • Claude にエラーメッセージが返ると、同セッション内で自動的に再試行 するか?
  • 2回目の tool_use は undefined を null に直すか?
  • Claude のリカバリー挙動 (エージェントとしての賢さ) を観察できる

問題3: 部分JSONを「途中で」可視化する

課題: Fine-grained streaming の真価は「途中の partial を見せる」こと。 content_block_stop を待たずに、partial_json を毎回受信するたび に「accumulator を json5/loose-json でゆるくパース」 → 取れた部分だけ UI 更新、というパターンを試せ。
ヒント: pip install json5 でゆるい parser を入れる。try: parsed = json5.loads(accumulated) で失敗してもエラーにしない。例えば「half-typed の string も読めるパーサー」を使えば、コードエディタのように文字単位で表示できる。
応用シナリオ
  • Claude.aiのArtifacts(コードを書きながらプレビュー表示)はこの方式
  • 長い array (例: lines_of_text: [...]) を 1行ずつエディタに表示 できる
  • ユーザーは「Claude が今書いている内容」を逐次見られる → 体感速度劇的向上

⑩ 中学生向けに例えると

学校の例えtool streaming の対応
先生が作文を最後まで書き終わってから「はい」と渡す通常streaming (JSON妥当化バッファリング)
先生が書きながら一文字ずつ机に出してくるFine-grained streaming (即時送出)
書きながら出すから途中で誤字が混ざってる可能性ありinvalid / partial JSONの危険性
「読み取った文字列が変だったら、丸ごと『これ変だよ』と先生に返す」INVALID_JSON ラッパー
「完成版が見たいだけ」なら待った方が安心普通の tools=[...] で良い
核心: ユーザー体感速度を上げたいときだけ Fine-grained を使う。普段は 普通の streaming で十分。

⑫ 理解度チェック

Q1. Fine-grained tool streaming が解決する問題は?

tool input (引数JSON) が長い (例: 1000行の詩・長いコード) とき、サーバー側のJSON妥当化バッファリング によってクライアントに届くまで遅延する問題。
Fine-grained を使うと 妥当化を省略 し、Claude が token を吐いた瞬間そのまま流す → 体感速度が劇的に上がる。

Q2. Fine-grained を使うとどんなリスクがある?

① invalid JSON がそのまま届く可能性 (Claudeが undefined 等を出すと素通り)
② max_tokens に到達した場合、tool input が 途中で切れて 不完全な状態で終わる
対策: json.loads を try/except で囲み、失敗時は {"INVALID_JSON": "..."} ラッパーで包んでClaudeに返す。

Q3. ipynb cell-4 で chunk.type == "input_json" のとき何をやっている?

chunk.partial_json を そのまま print(end="") で出力 している。
これは tool input が組み立たる過程をリアルタイムで画面に流す処理。Fine-grained streaming の体験を一番感じる場所。

Q4. 現行公式仕様での有効化方法は?

tool 定義に "eager_input_streaming": True を1行足す。tool 単位で個別に切り替えられる。
旧 beta header 方式 (betas=["fine-grained-tool-streaming-2025-05-14"]) は ipynb の実装に残っているが、現行公式仕様では eager_input_streaming が標準。
