Workflows vs agents— 結局どっち使うべき? — 選び方の最終整理

Anthropic Academy / コース02 Claude with the Anthropic API

① 結論ファースト

原則: まず Workflow で実装。動的判断が必要な部分だけ Agent 化。

最初から全部 agent 化は過剰設計。Anthropic 公式推奨でもある (2025-04 「Building effective agents」)。

② 一目で分かる比較

観点WorkflowAgent

③ 判断フローチャート

Q1: タスクの流れが事前に決まっている?
  Yes → Workflow へ
  No  → Q2 へ

Q2: 失敗時のコストが大きい (本番・SLA)?
  Yes → Workflow + 限定的 Agent (制約付き)
  No  → Q3 へ

Q3: 探索・調査・未知タスク?
  Yes → Agent
  No  → Workflow (default)

④ ハイブリッド構成 (実務おすすめ)

本番では Workflow を骨格にして、特定ステップだけ Agent 化 するのが主流。

# 例: カスタマーサポート
def support_pipeline(inquiry: str):
    # Step 1: Routing (workflow)
    category = classify(inquiry)

    # Step 2: カテゴリ別処理 (workflow or agent)
    if category == "refund":
        return refund_workflow(inquiry)   # 決まった手順
    elif category == "technical":
        return tech_agent(inquiry)        # 動的判断必要
    elif category == "billing":
        return billing_workflow(inquiry)  # 決まった手順
    else:
        return general_agent(inquiry)     # 未知の質問
ポイント: 「決まった手順」=workflow / 「臨機応変」=agent でステップごとに使い分け。

⑤ コース 02 で学んだ Workflow 5 パターン

  • Parallelization (#83): 独立タスクを並列実行 (asyncio.gather / Promise.all)
  • Chaining (#84): タスクを連鎖して逐次実行 (前段の出力を次段の入力に)
  • Routing (#85): 入力を分類して専用フローへ振り分け
  • Orchestrator-workers: マスターが子タスクに分割 (動的)
  • Evaluator-optimizer: 生成 → 評価 → 改善ループ

⑥ Agent 実装ベストプラクティス再掲

  1. 環境観察を最初に (#87 Environment inspection)
  2. tool は read-only から始める (副作用は後で)
  3. 終了条件を明確に (Claude の stop_reason をループ判定)
  4. memory (messages) で全履歴保持
  5. 失敗時はリトライ + 上限設定 (無限ループ防止)

⑦ 中学生向けに最終まとめ

Workflow = レシピ通りの料理 (確実・予測可能)
Agent = 自由創作料理 (柔軟・予測不能)
実務 = レシピをベースに自由な部分だけ任せる (ハイブリッド)

⑧ 理解度チェック

Q1. なぜ「まず Workflow」推奨?

A. 予測可能 / デバッグ容易 / コスト低 / SLA 守りやすい。Agent は柔軟だが予測不能で本番運用が難しい。

Q2. Agent 化が向く場面は?

A. 未知・探索系タスク。フローが事前に決まらない場合。ユーザー要望が毎回違う場合。

Q3. 実務で多いパターンは?

A. ハイブリッド構成。Workflow を骨格 → 動的判断が必要な部分だけ Agent 化。
