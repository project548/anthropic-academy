Model based grading— もう1人の Claude に採点させる

Anthropic Academy / コース02 Claude with the Anthropic API

① グレーダー(採点機)は3種類

図① 採点機3種類の特徴

グレーダー強み弱み
コード高速・低コスト・100%再現性「内容の質」を見るのは苦手
モデル(LLM)内容の質を評価できる・柔軟スコアにブレあり・API コストかかる
人間究極の柔軟性時間がかかる・スケールしない

この章は モデルグレーダー を実装する。柔軟性が高く、文章品質の評価に向いている。

② ★ コツ: 点数だけ求めると中庸スコアに偏る

あるあるの罠: 「この応答を10点満点で採点して」とだけ頼むと、Claude は 「とりあえず6点くらい」 と中庸に逃げる傾向がある。これでは v1 と v2 を比較できない。
解決法: 評価結果として strengths(良い点)・weaknesses(改善点)・reasoning(理由)・score(点数) の4点セットを求める。理由を先に考えさせると、Claude は真面目に採点してくれる。

③ 実装の3ステップ

1grade_by_model 関数を書く

評価プロンプトに「4点セット」を要求して、JSON で返してもらう。プレフィル+ストップで raw JSON 取得。

def grade_by_model(test_case, output):
    eval_prompt = f"""
    Evaluate the following solution...

    Task: {test_case['task']}
    Solution: {output}

    Provide your evaluation as a structured JSON object with:
    - "strengths": An array of 1-3 key strengths
    - "weaknesses": An array of 1-3 key areas for improvement
    - "reasoning": A concise explanation
    - "score": A number between 1-10
    """

    messages = []
    add_user_message(messages, eval_prompt)
    add_assistant_message(messages, "```json")
    eval_text = chat(messages, stop_sequences=["```"])
    return json.loads(eval_text)

2run_test_case に組み込む

ハードコード10をモデルグレーダー呼び出しに置き換える。

def run_test_case(test_case):
    output = run_prompt(test_case)

    model_grade = grade_by_model(test_case, output)
    score = model_grade["score"]
    reasoning = model_grade["reasoning"]

    return {
        "output": output,
        "test_case": test_case,
        "score": score,
        "reasoning": reasoning
    }

3run_eval で平均スコアを計算

プロンプト全体の最終メトリックを出す。

from statistics import mean

def run_eval(dataset):
    results = []
    for test_case in dataset:
        result = run_test_case(test_case)
        results.append(result)

    average_score = mean([r["score"] for r in results])
    print(f"Average score: {average_score}")

    return results

これで「プロンプト v1 = 平均 6.3」「v2 = 平均 8.1」のような 客観メトリック が手に入る。

④ モデルグレーダーの注意点

注意1: やや気まぐれ — 同じ応答でも、評価のたびにスコアが少しブレる。完璧な再現性は期待できない。
注意2: コスト2倍 — 評価のたびにもう1回 API 呼び出しが走る。生成 + 採点 で API コストは倍。Haiku 等の安いモデルを使うと節約できる。
許容範囲: 「だいたい同じ条件で比較できる」一貫性は確保できる。絶対精度よりも、相対比較 のために使う。

⑦ 理解度チェック

Q1. なぜ score だけを求めないの?

「点数だけ書いて」と頼むと Claude は中庸スコア(6点くらい)に逃げる傾向がある。strengths/weaknesses/reasoning/score の4点セットを求めることで、Claude が真面目に考えてから点数を出す状態を作る。

Q2. モデルグレーダーの欠点は?

① 同じ応答でもスコアが少しブレる(気まぐれ)、② 評価のたびにもう1回 API 呼ぶのでコスト2倍、③ 絶対精度よりも相対比較に向いている。

Q3. 全テストケースのスコアを統合する方法は?

statistics.mean() で平均を取る。プロンプト全体の最終メトリックとして使い、v1 と v2 を数値で比較できる。

Q4. コードグレーダーとモデルグレーダー、どう使い分ける?

フォーマット検証や有無チェック(JSON valid か等)はコード、文章品質や指示追従度はモデル。両方を組み合わせるのもアリ。
