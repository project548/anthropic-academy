④ 統合演習問題

1テストケース構造を設計する

お題: AWS 関連のコード支援プロンプトを評価する。3つのテストケースをどんな構造で書く?
💡 ヒント: #27 で format フィールドを追加したことを思い出す。validate_python / validate_json / validate_regex を選ぶ鍵。
答えを見る 
[
  {
    "task": "Create a Python function to validate an AWS IAM username",
    "format": "python"
  },
  {
    "task": "Generate an EventBridge rule for EC2 state changes",
    "format": "json"
  },
  {
    "task": "Write a regex to match AWS resource ARNs",
    "format": "regex"
  }
]

📍 ポイント: task で何をさせるか・format で期待出力形式を指定。

2run_test_case にモデル+コード両採点を組み込む

お題: #25 では score=10 ハードコード、#26 でモデル採点、#27 でコード採点を学んだ。両方の平均 を返すように書きなさい。
答えを見る 
def run_test_case(test_case):
    output = run_prompt(test_case)

    # モデル採点 (#26)
    model_grade = grade_by_model(test_case, output)
    model_score = model_grade["score"]
    reasoning = model_grade["reasoning"]

    # コード採点 (#27)
    syntax_score = grade_syntax(output, test_case)

    # スコア合成
    score = (model_score + syntax_score) / 2

    return {
        "output": output,
        "test_case": test_case,
        "score": score,
        "model_score": model_score,
        "syntax_score": syntax_score,
        "reasoning": reasoning
    }

📍 ポイント: 合成スコアだけでなく model_score と syntax_score を別々に保存しておくと、後で「どっちが悪いか」を分析できる。

3プロンプトを改善して点数を上げる

お題: ベースラインのプロンプト v1 を評価したら平均スコアが 5.2 だった。3つの改善案を考えなさい。
💡 ヒント: #27 のプロンプト改善のコツを思い出す(フォーマット明示・プレフィル・format ヒント)。
答えを見る

① 出力形式を厳密に指定:

  • Respond only with Python, JSON, or a plain Regex
  • Do not add any comments or commentary

② アシスタントメッセージにプレフィル:

add_assistant_message(messages, "```code")

③ format ヒントを Claude に伝える:

prompt = f"Task ({test_case['format']}): {test_case['task']}"

📍 結果イメージ: 5.2 → 7.8 のような改善が 客観点数で確認できる。これがプロンプト評価パイプラインの真価。

⑤ 完成パイプラインの全工程まとめ

  1. dataset.json 作成: generate_dataset() で test_case を Claude に作らせる(format 付き)
  2. プロンプト v1 を書く: シンプルなテンプレ
  3. run_eval(dataset): 各 test_case で run_prompt → model 採点 → syntax 採点 → 平均
  4. 平均スコアを記録: ベースライン取得
  5. プロンプト v2 を書く: 改善版(フォーマット指定・プレフィル・format ヒント)
  6. 再び run_eval: 平均スコア比較
  7. 反復: スコアが上がるまで繰り返す
核心: 「なんとなく良くなった気がする」を排除して、客観点数で改善幅を測る。これが本番品質のプロンプトを作る現実的なやり方。
