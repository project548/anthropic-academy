① 一言まとめ
Prompt Engineering の 2大技法。プロンプトに ガイドライン（guidelines） や ステップ（steps） を追加し、モデル出力を特定の方向に誘導する。
Type A（Attributes） = 出力の属性（What）を指定 / Type B（Steps） = 推論プロセス（How）を指定。両者の組み合わせがプロフェッショナルなプロンプトの定石。
アスリート食事プラン題材: 3.92 → 7.86（+3.94 = ほぼ 倍増）。Being Clear and Direct より遥かに大きい改善幅。ここで初めて「実用レベル」のプロンプトに到達。
② キーポイント
  • 1
    Being Specific = 2つのタイプに分かれる
    Type A（Attributes） = 出力に欲しい品質・属性をリスト（What）
    Type B（Steps） = モデルに推論プロセスのステップを提供（How）
    Type A は「特性」、Type B は「思考順序」を制御。
  • 2
    Type A: Attributes（属性ガイドライン）
    出力の 長さ / 構造 / フォーマット / トーン / 含めるべき要素 / 制約 をリスト化。
    例: 「朝食/昼食/夕食/おやつ の4区分で構成」「カロリー kcal で明示」「マクロ栄養素 g 単位」「食事制限を厳守」
    ほぼすべてのプロンプトで推奨される基本技法。フォーマット統一が必要な業務プロンプトで特に有効。
  • 3
    Type B: Steps（ステップガイドライン）
    モデルが 「どう考えるか」 の順序付き手順を提供。
    例: ① 総カロリー目標を算出 → ② マクロ比率で配分 → ③ 食事制限に違反しない食材選択 → ④ 4区分に配分 → ⑤ 構造化出力
    複雑な問題で、モデルに広い視野で考えてほしい時 / 自然には考慮しない視点を強制したい時に決定打。
  • 4
    両者の組み合わせがプロフェッショナル
    プロのプロンプトでは Type A + Type B を併用するのが標準。
    Type B（思考順序）→ Type A（出力仕様）の順で書くと、推論プロセスから出力品質まで両方制御できる。
  • 5
    スコア改善: 3.92 → 7.86（ほぼ倍増）
    Being Clear and Direct 適用後（v2: 3.92）→ Being Specific 適用後（v3: 7.86）。
    +3.94 = ほぼ倍増。Being Clear and Direct（+1.6）より遥かに効く。ここで初めて「実用レベル」に到達。
  • 6
    なぜ Type B が劇的に効くか = Chain-of-Thought 原理
    LLM は逐次トークン生成（前のトークンが次に影響）。「いきなり最終答えを出せ」だと構造化されない。
    「①→②→③ の順で考えろ」と指示すると 各ステップで思考が整理 され、論理的整合性が向上。これが Chain-of-Thought（CoT）プロンプティングの原理。
  • 7
    落とし穴（Pitfalls）
    ❌ ステップが多すぎる（10超は逆効果。4-6 が最適）
    ❌ 矛盾するガイドライン（"短く" + "詳しく分析" 等）
    ❌ 抽象的すぎるステップ（「よく考えて」「丁寧に」は無効）
    ✅ 動詞 + 具体的な対象 で書く
③ Type A vs Type B（判断基準）
軸 Type A（Attributes） Type B（Steps）
制御対象 What（何を含めるか） How（どう考えるか）
形式 箇条書き（bullet list） 番号付きリスト（1, 2, 3...）
典型例 "must include kcal" "use clear headers" "First, calculate total calories. Second, distribute macros..."
使い所 ほぼ全プロンプト（必須） 複雑な推論・計算が必要な時
効果 フォーマット統一・出力品質安定 論理整合性向上・抜け漏れ削減
リスク ほぼノーリスク 多すぎると逆効果（4-6 が最適）
判断軸: シンプルなタスク（要約・分類）なら Type A だけで十分。複雑な推論・計算が絡むなら Type A + Type B 併用が決定打。
④ 組み合わせ例（meal plan）
Generate a one day meal plan for an athlete. [Type B: Steps] 1. Calculate total daily calories based on the physical goal. 2. Distribute calories across macronutrients (protein/carbs/fat) at 30/40/30 ratio. 3. Build meal combinations that respect dietary restrictions. 4. Organize into breakfast/lunch/dinner/snack structure. [Type A: Attributes] - Each meal must include kcal and macros (g) - Specify nutritional purpose per meal (1 line) - Strictly avoid restricted ingredients - Use clear section headers
この構造で 思考プロセス（Type B）+ アウトプット仕様（Type A）の両方 を制御。スコア 3.92 → 7.86 に到達した実装パターン。

⑥ 理解度チェック
Q1
Type A と Type B の違いを「制御対象」「形式」「使い所」の3軸で説明してください。
答えを見る
Type A（Attributes）:
・制御対象 = What（何を含めるか / 出力の特性）
・形式 = 箇条書き（"must include kcal" "use clear headers"）
・使い所 = ほぼ全プロンプト（必須）

Type B（Steps）:
・制御対象 = How（どう考えるか / 推論プロセス）
・形式 = 番号付きリスト（"First, calculate. Second, distribute..."）
・使い所 = 複雑な推論・計算が必要な時（4-6 ステップが最適）
Q2
なぜ Type B（ステップ追加）が劇的にスコアを上げるのですか？
答えを見る
LLM は 逐次的にトークンを生成（前のトークンが次のトークンに影響）する仕組み。
「いきなり最終答えを出せ」と言うと、構造化されない生成になる。
「①→②→③ の順で考えろ」と指示すると、各ステップで思考が整理 され、中間ステップが後続の推論を補強する。
これは Chain-of-Thought（CoT） プロンプティングの原理。Type B で抜け漏れ・論理矛盾が大幅に減るため、スコアが劇的に向上する。
Q3
Type B のステップを設計する時に避けるべき落とし穴を3つ挙げてください。
答えを見る
❌ ステップが多すぎる: 10ステップ超はモデルが混乱。4-6 ステップが最適。
❌ 矛盾するガイドライン: Type A で「短く」と言いつつ Type B で「詳しく分析」など → 整合性を保つ。
❌ 抽象表現: 「よく考えて」「丁寧に」は無効。動詞 + 具体的な対象（"calculate calories" "distribute macros"）で書く。
これらを守れば Type B の効果を最大化できる。
