Module 3 ・ Lecture 113 ・ コード変更

Making changes— Claude にコードを変更させるベストな指示の出し方

Anthropic Academy / コース04 Claude Code

① 基本フロー

  1. 指示: 自然言語で「○○して」と伝える
  2. 計画提示: Claude が「これからこう変更します」と宣言
  3. diff 確認: 各 Edit ごとに承認 / 拒否を選択
  4. 検証: テスト・lint・型チェックを Claude 自身が実行
  5. 追加修正: 結果見て次の指示
核心: Claude は 承認なしでファイルを上書きしない。diff 表示 → ユーザー承認のステップを必ず踏む。

② 良い指示・悪い指示

  • ❌ 「いい感じに直して」 → 何を直すか不明 / 曖昧
  • ❌ 「全部リファクタして」 → スコープ広すぎ / 副作用大
  • ✅ 「auth.ts:42 の any 型を厳密な型に書き換えて」 → 場所と目的が明確
  • ✅ 「ログイン失敗時のエラーメッセージを日本語化。messages.ts に集約」 → スコープと方針が明確

③ 大きい変更は段階分割

# ❌ 一気に全部
> auth 全体を JWT に書き換えて

# ✅ 段階分割
> まず JWT 関連の依存を package.json に追加して
> 次に utils/jwt.ts を新規作成 (sign / verify)
> その次に login.ts で sign 呼び出しに置き換え
> 最後に middleware で verify 呼び出し

# 各ステップで diff 確認 → テスト → 次へ

④ diff 承認の選択肢

  • Approve: そのまま適用
  • Reject: 適用しない・指示やり直し
  • Edit: 内容を手動修正してから適用
  • Approve All: 一連の変更を全部一括承認 (注意・診断必須)

⑤ 「失敗」を活かす指示

  • テスト失敗 → 「失敗ログを読んで修正して」
  • 型エラー → 「tsc --noEmit で出たエラーを直して」
  • lint エラー → 「npm run lint 実行して全エラー解消」
  • 意図と違う出力 → 「ここは△△にしたかった。直して」

Claude は 失敗ログを読んで自己修正 できる。エラーを隠さず見せるのが正解。

⑥ 安全装置 (デフォルト)

  • ファイル変更前に必ず diff 表示
  • Bash 実行は承認待ち (危険コマンドは特に)
  • git status 等の read-only は自動許可
  • git 操作は明示指示が必要 (commit/push は手動)
  • 本番デプロイ系コマンドはブロック (settings で制御可)

⑦ 中学生向けに例えると

料理ロボに「カレー作って」と頼んだとき、「玉ねぎを切ります、いいですか?」と毎回確認するのが Claude Code。「OK」「いや、もっと細かく」と指示し直せる。雑な指示より具体的な指示の方が出来も早い。
