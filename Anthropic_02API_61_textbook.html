Rules of prompt caching— キャッシュが効く条件・無効化ルール・落とし穴まとめ

Anthropic Academy / コース02 Claude with the Anthropic API

① まず結論 — このレクチャーで覚えるルール

#60 (Prompt caching) で機能の輪郭はわかった。本章は 「キャッシュ命中する条件」と「無効化の条件」 を厳密に押さえる回。本番運用ではここを知らないと「思ったよりキャッシュが効かない」事故が起きる。

5つの大原則:
  1. 階層順序 = tools → system → messages (この順で前方一致)
  2. ハッシュ完全一致 = 1文字違うとミス
  3. breakpoint 最大4個 / 1リクエスト
  4. lookback 20ブロック / breakpoint
  5. 最小トークン: Opus 4.5+ = 4096 / Sonnet 4.6+ = 1024 / Haiku 4.5 = 4096

② キャッシュ対象になる/ならない

キャッシュOKキャッシュNG
  • tools 配列内のtool定義
  • system 配列内のtextブロック
  • messages.content のtext
  • messages.content の image / document (userのみ)
  • tool_use と tool_result ブロック
  • thinking blocks に cache_control 直接指定不可
  • sub-content blocks (citations等) を直接キャッシュ不可
  • 空のtext block

③ 階層順序 — tools → system → messages

[tools 定義]      ← 最初に評価
   ↓
[system messages] ← 次に評価
   ↓
[messages 配列]   ← 最後に評価 (時系列順)
   ↓
[breakpoint]
核心: 後段が変わると後段だけミスする。前段が変わると後段も全部ミス。
→ 「変わらないもの」を 前段 に置くアーキテクチャ設計が必要。

④ ハッシュベース完全一致

# キャッシュ書き込みは breakpoint の位置のみ
# 「breakpoint までのプレフィックスのハッシュ」が1個記録される

# 一致判定:
# 次回リクエストで同じプレフィックスハッシュなら HIT
# 1文字でも違えば MISS
「ほとんど同じ」では効かない:
  • system promptに「今日は2026-05-23」など 毎回変わる文字 を入れる → 毎回MISS
  • 絵文字・空白・改行コード(LF/CRLF)の違い → MISS
  • tool_choiceの設定変更 → MISS
  • JSONキーの順番が違う (一部言語のSDK)→ MISS

⑤ Lookback の20ブロック制約

Turn 1: 10ブロック + breakpoint → block 10 にキャッシュ書込
Turn 2: 15ブロック + breakpoint → block 10 を発見 (lookback 5) → HIT
                                  → block 15 にも新キャッシュ書込
Turn 3: 35ブロック + breakpoint → 35-16=19ブロックさかのぼる → 範囲外 → MISS!
                                  → 解決策: block 15 にも追加 breakpoint
解決策: 長い会話履歴では 中間に breakpoint を追加 して、20ブロック範囲内にcache を保持する。

⑥ 無効化マトリクス — 何が変わると何が壊れる?

変更内容tools cachesystem cachemessages cache
tool 定義変更✘✘✘
web_search トグル✓✘✘
citations トグル✓✘✘
Speed設定 (fast/standard)✓✘✘
tool_choice パラメータ✓✓✘
image 追加/削除✓✓✘
thinking パラメータ✓✓✘
読み方: ✓ = キャッシュ生存 / ✘ = 無効化。上層 (tools) を変えると下層 (system / messages) も全部死ぬ。これが 階層の波及。

⑦ 最小キャッシュサイズ — モデル別

モデル最小

Sonnet 4.6 / 4.5 / Opus 4.11,024 tokens

注意: 最小未満は エラーなくキャッシュされない。cache_creation_input_tokens=0 で気づく。

⑧ TTL ルール — 5分 vs 1時間

設定TTLcache_creation 料金
{"type":"ephemeral"}5分1.25倍 (標準)
{"type":"ephemeral","ttl":"1h"}1時間2.0倍 (extended)

混在ルール: 同じリクエスト内で TTL を混ぜる場合、1時間が先・5分が後 の順で並べる必要あり。

TTLは毎アクセスでリセット: 5分以内に次のリクエスト来る → cache 生き続ける (実質永続)。

⑨ Pre-warming (事前ウォームアップ)

# ユーザーが来る前にキャッシュを温める
prewarm = client.messages.create(
    model="claude-opus-4-7",
    max_tokens=0,  # 出力ゼロ (放棄)
    system=[
        {
            "type": "text",
            "text": "あなたのsystem prompt...",
            "cache_control": {"type": "ephemeral"},
        }
    ],
    messages=[{"role": "user", "content": "warmup"}],
)
# → stop_reason="max_tokens", content=[]
# → cache_creation 料金は発生 (キャッシュ書込のみ)
使い所: 毎日朝にユーザーが来る前にcache 温めておく。最初のユーザーが「初回 cache_creation 料金 + 待ち時間」を払わなくて済む。
NG: stream=true / extended thinking / structured outputs / 特定の tool_choice / Message Batches では pre-warm 不可。

⑩ 並行リクエストの罠

# NG: 並行5本
[req1] [req2] [req3] [req4] [req5]  ← 同時起動
↓
全部 cache_creation 発生 (5倍課金!)

# OK: 順次1本目を待つ
[req1] → 完了 → cache 完成 → [req2,3,4,5] 並行 → 全部 cache_read
解決: 大量並行処理する場合は、1リクエストだけ先行 → 完了確認後に残りを並列。

⑪ Workspace / Organization 分離

  • キャッシュは 組織レベルで分離 (他社とは絶対共有しない)
  • 2026-02-05以降: Claude API / AWS / Microsoft Foundry で Workspaceレベル分離
  • Bedrock / Vertex AI: 組織レベル分離のみ
セキュリティ的意味: 同じプロンプトを複数組織が使ってもキャッシュは絶対共有されない。プロンプト本文が漏れることはない。

⑫ Usage オブジェクトでデバッグ

"usage": {
  "cache_creation_input_tokens": 5120,
  "cache_read_input_tokens": 100000,
  "input_tokens": 50,
  "cache_creation": {
    "ephemeral_5m_input_tokens": 5000,
    "ephemeral_1h_input_tokens": 120
  }
}

# 計算式:
# 総 input tokens = cache_read + cache_creation + input_tokens

# デバッグ判定:
# cache_creation=0 かつ cache_read=0 → 全くキャッシュされていない
# → minimum tokens を満たしてない / breakpoint 配置間違い等を疑う

⑬ よくある落とし穴 (運用前に潰す)

落とし穴1: timestamp を system に入れる

「現在時刻: 2026-05-23 14:30」をsystem promptに含めると毎リクエストMISS。
→ 時刻はmessages 末尾のuserメッセージに含めて、systemは時刻無しに。

落とし穴2: breakpoint を変わる箇所に置く

毎回違うユーザー質問の直前に breakpoint を置く → そこにキャッシュ書込が発生するが、毎回ハッシュ違うので絶対HITしない。
→ breakpoint は 「変わらない最後のブロック」 に置く。

落とし穴3: JSONキー順番の非決定性

Swift・Goは dict iteration がランダム → 毎回キー順が違うと cache MISS。
→ sort_keys=True 相当 or 明示的にOrderedDictで安定化。

落とし穴4: 20ブロック超え

会話履歴が20ブロック超えると lookback 範囲外 → MISS。
→ 10ブロックごとに自動 breakpoint を追加するロジックを書く (最大4個まで)。

落とし穴5: image 追加で messages cache 死亡

画像を1枚追加するだけで messages cache 全死。
→ 画像入りのリクエストは別ルーティング / image-only セッションを切り出す。

⑭ 中学生向けに例えると

学校の例えcaching rules の対応
机に「全く同じ教科書」が置いてあれば借りずに使えるハッシュ完全一致が必要
1文字違うだけで「別の本」扱い1byte違いで MISS
「本」「ノート」「メモ」の順番でしか積めないtools→system→messages 階層
「本」を変えるとノートもメモも置き直し上層変更が下層を全死

核心: 「同じ」の定義が厳密。バイト単位で揃えるアーキテクチャ設計が必要。デバッグは usage オブジェクトで cache_read を見る。

⑯ 理解度チェック

Q1. キャッシュの階層順序は?

tools → system → messages。この順で前方一致 (prefix matching) が評価される。上層が変わると下層全部MISSになる。

Q2. breakpoint はいくつまで?

1リクエスト最大4個。長い会話履歴では中間にも breakpoint を置いて lookback 20ブロック制限を回避する。

Q3. Opus 4.7 の最小キャッシュサイズは?

4,096トークン。これ未満はキャッシュされず、エラーも出ない (silent fail)。cache_creation_input_tokens=0 で気づく必要あり。

Q4. 一番ハマる落とし穴は?

system promptに timestamp 等の毎回変わる文字を入れること。1文字でも違うと完全MISS。時刻情報は messages 末尾 (breakpoint より後ろ) に置くのが鉄則。

Q5. 並行リクエストの罠は?

キャッシュは 最初のレスポンス開始後 に利用可能になる。同時に5本投げると全部 cache_creation 発生 → 5倍課金。1本目完了を待ってから残りを並列実行する。
