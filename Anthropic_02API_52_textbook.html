Text embeddings— テキストを数百次元のベクトルに変換して「意味の近さ」を測る

Anthropic Academy / コース02 Claude with the Anthropic API

① まず結論 — embeddingって何?

テキストを 数値のリスト (ベクトル) に変換する技術。例えば「猫」を [0.12, -0.34, 0.87, ..., 0.05] という1024次元の数値列にする。

同じことを「犬」「ネズミ」「自動車」でやると、意味が近いものほどベクトル空間で近い場所 に配置される。

核心: embedding を使うと「猫」と「猫科の動物」が文字列としては違っても、ベクトル空間で 近い ことが計算で分かる。これが セマンティック (意味) 検索 の基盤。

② どんな空間? — 視覚化

図① 意味が近いテキストは空間内で近くに配置される

実際は1024次元 (Voyage AI voyage-3-large)。2D の絵では伝わらない繊細な意味関係 (動詞・形容詞・文脈) が高次元空間でモデル化される。

③ ipynb 002 の実装 — Voyage AI を使う

# pip install voyageai
from dotenv import load_dotenv
import voyageai

load_dotenv()
client = voyageai.Client()

def generate_embedding(text, model="voyage-3-large", input_type="query"):
    result = client.embed([text], model=model, input_type=input_type)
    return result.embeddings[0]

# 使い方
chunks = chunk_by_section(text)
vector = generate_embedding(chunks[0])
# → [0.12, -0.34, 0.87, ..., 0.05] (1024個の数値)

④ input_type の使い分け — query vs document

input_type用途
"document"事前準備時: 文書chunkをembeddingして保存するとき
"query"検索時: ユーザーの質問をembeddingするとき
なぜ分ける? 質問と文書は表現スタイルが違う (質問は短く・疑問形 / 文書は長く・宣言形)。
input_type を指定することで、それぞれに最適化された embedding が得られる → 検索精度向上。

⑥ 類似度の計算 — 2つの方法

手法計算式用途
Cosine類似度2ベクトルのなす角度RAG標準。長さに依存しない
Euclidean距離普通の直線距離 (ピタゴラス)位置情報が意味を持つ場合
 
# Cosine類似度の核心 (本コース #53 VectorIndex で使用)
def cosine_distance(vec1, vec2):
    dot_product = sum(a*b for a,b in zip(vec1, vec2))
    mag1 = math.sqrt(sum(x*x for x in vec1))
    mag2 = math.sqrt(sum(x*x for x in vec2))
    cosine_similarity = dot_product / (mag1 * mag2)
    return 1.0 - cosine_similarity  # 距離なので 1-cos
Cosine類似度: 1 (完全一致) 〜 -1 (正反対) の範囲。
Cosine距離: 0 (完全一致) 〜 2 (正反対)。検索では距離が 小さい順 にトップk件を取る。

⑧ オリジナル演習問題 (2問)

問題1: 似た意味の文を3組作って、cosine類似度を計算してみる。
例:
  • 「今日は晴れだ」 vs 「本日の天気は良好」 → 類似度高いはず
  • 「猫が好き」 vs 「犬が嫌い」 → 中程度
  • 「Python のプログラム」 vs 「明日の朝食」 → 低い
問題2: input_type を "query" と "document" で同じテキストをembeddingし、cosine類似度を測る。
→ 完全に同じテキストでも 0.99 程度の類似度 (1.0ではない) になる。これが「同じ文も query/document で別ベクトルになる」証拠。

⑪ 理解度チェック

Q1. embedding の目的は何?

テキストを 数値ベクトル に変換し、「意味が近いテキストはベクトル空間で近くに配置」させること。これによって、文字列が違っても 意味の近さ で検索できる (セマンティック検索)。

Q2. なぜ input_type を query/document で分ける?

質問文と文書本文は表現スタイルが違う (短い疑問 vs 長い宣言)。別々の input_type で embedding することで、それぞれに最適化されたベクトルが得られ、検索精度が向上する。

Q3. Cosine類似度と Euclidean距離の使い分け?

RAGでは Cosine類似度がデフォルト。理由: ベクトルの「方向」だけで意味を判定し、長さ (大きさ) に依存しない。長文と短文が混在する場合でも公平に類似度判定できる。

Q4. 1024次元って多すぎないの?

むしろ十分な情報量を保つのに必要。GPT時代以前は300次元前後だったが、複雑な意味関係 (文脈・否定・比喩) を表現するには高次元が有効。voyage-3-large の1024次元は 性能とコストのバランス 良い値。
