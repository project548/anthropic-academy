① 一言まとめ

題材は「アスリート向け1日分の食事プラン生成」。意図的に質の低い初期プロンプト（平均スコア≈2.32）からスタートし、Being Clear and Direct → Being Specific → XML Tags → Providing Examples 等の技法を1つずつ適用 → 段階的にスコアを上げていく。

③ 3つの主要コンポーネント詳細
コンポーネント 役割 例
prompt_input_spec プロンプトに必要な入力を定義する dictionary。generate_dataset() がこの spec に基づいてテストケースを自動生成。 {"height": "cm", "weight": "kg", "physical_goal": "...", "dietary_restrictions": "..."}
extra_criteria Model Grader に「特に重視して評価して」と伝える追加基準。Grader プロンプトに組み込まれる。 「食事制限を厳守しているか」「カロリーがゴールに合致しているか」
output.html eval 実行結果を HTML レポートとして可視化。改善サイクルでの効果検証に必須。 各テストケース: 入力 / プロンプト / 出力 / Model Score / Syntax Score / Final Score / reasoning
output.html の威力: ただスコア平均を見るだけでなく、「どのテストケースで低スコア？」「reasoning から何が問題？」が一目で分かる → 次の技法選択の指針になる。
④ 改善サイクル（6ステップ）
Step アクション アウトプット
1 初期プロンプトを書く v1 プロンプト
2 テストケースの入力値を埋め込む 各テストケース別の完全プロンプト
3 eval パイプラインで実行 baseline 平均スコア（例: 2.32）+ output.html
4 1つの技法を適用 v2 プロンプト
5 再評価 v2 平均スコア + 改善幅（例: +1.6 = 3.92）
6 次の技法に進む（Step 4 へループ） v3, v4 ... と段階的改善
このモジュール後半で学ぶ技法: Being Clear and Direct（明確化）→ Being Specific（具体化）→ Structure with XML Tags（構造化）→ Providing Examples（例示）。各レクチャーで1つずつ深掘り。

⑥ 理解度チェック
Q1
なぜ「初期プロンプトを意図的に悪く書く」のですか？
答えを見る
改善余地を見せるため。最初から完璧なプロンプトだと「技法を適用してもスコアが上がらない」ので、各技法の効果を検証できない。
意図的にスコア2.32 程度に落としておくことで、Being Clear → 3.92、Being Specific → 7.86 のように各技法の効果が 段階的なスコア改善 として可視化される。これが「研究」のやり方。
Q2
3つの主要コンポーネント（prompt_input_spec / extra_criteria / output.html）はそれぞれ何の役割？
答えを見る
prompt_input_spec: プロンプトに何を入れるかの「入口の仕様」。generate_dataset() がこの spec を見てテストケースを自動生成。
extra_criteria: Model Grader への「特に重視して評価してほしい」追加指示。タスク固有の評価観点（食事制限厳守等）を Grader プロンプトに組み込む。
output.html: eval 結果の「出口の可視化」。スコア平均だけでなく、テストケース別の入力/出力/reasoning が一目で分かる → 次の技法選択の判断材料。
Q3
「主観改善」と「客観改善（eval ベース）」の本質的な違いは？
答えを見る
主観改善 ❌: 「なんとなく良くなった気がする」→ 改善が定量化できない / どの技法が効いたか分からない / 後戻りしても気付かない。
客観改善 ✅: 平均スコアが数値で改善幅を示す / 各技法ごとに効果を分離計測 / 後戻り（スコアダウン）を即座に検知 / データドリブンな最適化サイクル。
本質: 「研究」と「迷走」の境目は 各技法の効果を独立に分離計測できるか。eval を整えたからこそ、技法習得が積み上げ式に効く（これが22-27の eval モジュールの真価）。
