Introducing Retrieval Augmented Generation— RAG = LLMの「知らない情報」を外から渡す技法

Anthropic Academy / コース02 Claude with the Anthropic API

① まず結論 — RAGって何?

Claude (LLM) は学習データの範囲内しか知らない。
あなたの会社のドキュメント / 社内Wiki / 非公開資料 / 顧客データ — これらは絶対に知らない。

RAG (Retrieval Augmented Generation) = 「外部資料を検索 → 該当箇所だけ取り出して → Claudeに見せる → 答えてもらう」 のパターン。

3つの動詞: Retrieval (検索) → Augmented (拡張) → Generation (生成)
→ 「検索で材料を集めて、それを Claude のプロンプトに足して、生成させる」

② なぜ RAG が必要? — 4つの理由

理由説明
① 知識カットオフClaude は学習日以降を知らない (例: 今日のニュース)
② 私的情報社内資料・顧客カルテ・社員名簿は学習されていない
③ 大量資料10万件のFAQをcontextに入れるのはコスト爆発
④ 出典明示「どの資料の何ページに書いてあるか」を返せる(法務・医療・金融で必須)

③ RAG の全体フロー — 5ステップ

図① RAG の全工程 — 事前準備 3ステップ + 実行 2ステップ

核心: 事前準備 (1-3) は 1回だけ。実行 (4-5) は ユーザー質問が来るたびに毎回。準備さえ済めば、検索+生成は1秒以内で動く。

④ RAG vs 他の選択肢 — どう選ぶ?

選択肢適する場面限界
① 全文をプロンプト
(long context)		 資料が 10万トークン以下 / 質問が幅広い 大量だとコスト・速度が爆発
② RAG 資料が 大量 / 関連部分だけ欲しい / 出典必要 chunking設計・検索精度の調整必要
③ Fine-tuning 応答パターンの調整 / 専門用語の語彙 知識更新できない / 訓練コスト高
④ Tool use (検索) Web上の最新情報 / 動的データ 社内資料には使えない
Anthropic公式の指針: 資料が 20万トークン以下 でClaude 4の long context で収まるなら、RAG より full context の方が精度高い。
ただし 100万トークン超の社内資料・大量FAQ なら RAG 必須。

⑥ よくある誤解 — Q&A

「RAGするなら fine-tuning は不要?」

違う。役割が違う。
RAG = 「知識を渡す」(事実情報の供給)
Fine-tuning = 「振る舞いを変える」(応答スタイル・専門用語の使い方)
→ 両方併用するアプリも多い (例: 医療チャット = 医療RAG + 医療用語Fine-tuning)。

「Vector store ってどれを使えばいい?」

規模で選ぶ:
① 学習用・小規模 → 自前実装 (本コース ipynb の VectorIndex クラス)
② 中規模 (〜100万チャンク) → Chroma / Qdrant
③ 大規模 → Pinecone / Weaviate / pgvector
④ AWS統合 → OpenSearch / RDS pgvector
→ 本コースは ① で 仕組みを理解 することが目的。

「Embedding model はどれを?」

Anthropic は Voyage AI を公式推奨 (買収済み)。日本語含む多言語対応。
無料枠あり (https://www.voyageai.com)。本コース ipynb 002 で API key 取得方法あり。

⑦ 中学生向けに例えると

学校の例えRAG の対応
図書館にある百科事典を頭に丸暗記Fine-tuning (大変・更新困難)
百科事典1冊を授業中に開きっぱなしで質問対応Long context (全文プロンプト)
「○○について聞かれたら本棚の何巻何ページ見て答えて」RAG (検索→該当ページ参照→回答)
図書館の目録カード(キーワード索引)BM25 lexical search
図書館の意味検索 (似たトピックの本を探す)Embedding + vector search
核心: 全部を暗記しないで「どこに何が書いてあるか」と「該当ページを開いて確認する力」を持つ。これが RAG。

⑨ 理解度チェック

Q1. RAG の "R" "A" "G" は何の頭文字?

Retrieval (検索) + Augmented (拡張) + Generation (生成)。
「検索で材料を集めて、プロンプトに足して、生成させる」を3単語に圧縮したもの。

Q2. なぜ Fine-tuning ではなく RAG が選ばれるのか?

① 知識の更新: RAGはvector storeを更新するだけ。Fine-tuningは再訓練必要
② 出典明示: 検索で取ったチャンクの url/page番号を引用できる
③ コスト: 訓練不要・小規模事業者でも使える
④ 幻覚抑制: 「資料に書いてあること以外答えるな」と縛りやすい

Q3. Long context (全文プロンプト) と RAG はどう使い分ける?

資料サイズ・更新頻度・出典必要性で判定:
・10万トークン以下 + 全部読ませたい → Long context (シンプル・精度高)
・100万トークン超 / ピンポイントに該当部分が欲しい → RAG (コスト効率)
・出典必須 (法務・医療) → RAG (chunk url 付き)
→ 境界域なら両方試して精度・コスト比較する。

Q4. RAGの構成要素4パーツは?

① Chunker (分割) ② Embedder (ベクトル化) ③ Vector Store (保存+検索) ④ Lexical Search (補完的キーワード検索・BM25等)
本コースでは #51-#55 で各パーツを順番に学ぶ。
