① まず結論 — BM25って何?

BM25 (Best Match 25) は 1994年 (!) に開発された キーワードベース の検索アルゴリズム。Elasticsearch・Lucene・Solr の中核。30年現役。

核心: 「クエリの単語と一致する単語が、文書中にどれだけ含まれるか + どれだけ珍しい単語か」で点数化。embedding と違って 厳密な単語一致 を重視する。

② BM25 vs Embedding (semantic search) の違い

観点BM25 (lexical)Embedding (semantic)
得意固有名詞・型番・専門用語同義語・言い換え・概念

例: "晴れの日の服装"× "晴れ"も"服装"も無い文書はヒット不能○ 「快晴」「洋服」も近いと判定

結論: 両方使う (hybrid search) が正解。embedding で意味検索 + BM25 でキーワード検索 → 結果をマージ。

③ BM25 のスコア計算 — 直感的理解

各 chunk に対してクエリ単語ごとに以下を計算 → 合計:

score = Σ_{token in query} IDF(token) × TF_normalized(token, doc)

# IDF (Inverse Document Frequency): 単語の珍しさ
#   = log((N - df + 0.5) / (df + 0.5) + 1)
#   N = 全文書数 / df = その単語を含む文書数

# TF (Term Frequency): 単語の出現頻度 (BM25は飽和関数で正規化)
#   = (tf * (k1+1)) / (tf + k1*(1 - b + b*(doc_len/avg_doc_len)))
3つの調整パラメータ:
  • k1 (デフォルト1.5): 単語頻度の飽和速度。大きいと「同じ単語が多く出る = もっと関連」
  • b (デフォルト0.75): 文書長正規化。1なら長文ペナルティ強 / 0なら長さ無視
  • IDF: 珍しい単語に高い重み。「the / は / が」のような頻出語は無視される

④ ipynb 004_bm25.ipynb の BM25Index 実装

class BM25Index:
    def __init__(self, k1=1.5, b=0.75, tokenizer=None):
        self.documents = []          # 元 chunk リスト
        self._corpus_tokens = []     # 各文書のtoken化結果
        self._doc_len = []           # 各文書の長さ
        self._doc_freqs = {}         # 単語ごとに何文書に出るか
        self._idf = {}               # 単語ごとのIDF
        self.k1 = k1
        self.b = b
        self._tokenizer = tokenizer or self._default_tokenizer

    def _default_tokenizer(self, text):
        text = text.lower()
        tokens = re.split(r"\W+", text)
        return [t for t in tokens if t]

    def add_document(self, document):
        """文書追加: tokenize → 統計更新"""
        doc_tokens = self._tokenizer(document["content"])
        self.documents.append(document)
        self._corpus_tokens.append(doc_tokens)
        self._update_stats_add(doc_tokens)

    def _calculate_idf(self):
        """IDF算出: log((N - df + 0.5) / (df + 0.5) + 1)"""
        N = len(self.documents)
        for term, freq in self._doc_freqs.items():
            self._idf[term] = math.log(((N - freq + 0.5) / (freq + 0.5)) + 1)

    def search(self, query_text, k=1):
        """検索: 全文書とBM25スコア計算 → 上位k件"""
        query_tokens = self._tokenizer(query_text)
        raw_scores = []
        for i in range(len(self.documents)):
            raw_score = self._compute_bm25_score(query_tokens, i)
            if raw_score > 1e-9:
                raw_scores.append((raw_score, self.documents[i]))
        raw_scores.sort(reverse=True)
        return raw_scores[:k]
BM25 の落とし穴: デフォルトの re.split(r"\W+") は 日本語に弱い (単語境界が曖昧)。日本語chunkには MeCab / SudachiPy 等の形態素解析器を tokenizer に渡す必要あり。

⑤ Hybrid search — embedding + BM25

本番アプリでは両方使う。2段階パターンが定番:

# パターン1: 結果マージ (Reciprocal Rank Fusion)
semantic_results = vector_store.search(query, k=10)
lexical_results = bm25_store.search(query, k=10)

# 両方の結果から重複除去 + ランクスコア合算
def reciprocal_rank_fusion(rank_lists, k=60):
    scores = {}
    for rank_list in rank_lists:
        for rank, doc in enumerate(rank_list):
            doc_id = doc["id"]
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    return sorted(scores.items(), key=lambda x: -x[1])

merged = reciprocal_rank_fusion([semantic_results, lexical_results])
top_5 = merged[:5]  # 最終的に Claude に渡すchunk
効果: Anthropic の Contextual Retrieval ブログによると、embedding単体より 15-30%精度改善。特に固有名詞・型番・専門用語を含むクエリで顕著。

⑥ BM25 のメリット / デメリット

メリットデメリット
  • 無料 (API不要)
  • 計算超高速 (転置index)
  • 説明可能性 (なぜヒットしたか明確)
  • 固有名詞・型番・専門用語に強い
  • 追加学習不要
  • 同義語に弱い (「車」と「自動車」が別物)
  • 多言語混在テキストに弱い
  • tokenizer の品質依存 (特に日本語)
  • シノニム辞書を別途整備が必要なこともある

⑨ 理解度チェック

Q1. BM25 と embedding はどう使い分ける?

BM25 = 固有名詞・型番・専門用語の 厳密一致 に強い。
embedding = 同義語・言い換え・概念の 意味検索 に強い。
→ 本番では 両方使う (hybrid search) のが定石。RRF 等で結果をマージ。

Q2. IDF が必要な理由は?

「は」「が」「the」のような どこにでもある単語 でヒットしても意味がない。
IDF は「文書全体での出現頻度」の逆数で重み付け。珍しい単語ほど高スコア → クエリの本質単語が効くようになる。

Q3. なぜ日本語で BM25 を使うときに注意が必要?

デフォルト tokenizer (re.split(r"\W+")) は 空白で区切る ため、日本語に弱い (「今日は晴れだ」が1 tokenになる可能性)。
MeCab / SudachiPy 等の形態素解析器を tokenizer に渡す必要あり。

Q4. BM25 が30年現役なのはなぜ?

① 無料・高速・スケーラブル ② 説明可能性 (なぜヒットしたかが単語レベルで明確) ③ 厳密一致 (固有名詞・型番・コード) で embedding に勝る場面が多い ④ Elasticsearch等のインフラが整備済み
→ 「embedding に置き換わる」ではなく「embedding と併用して相補」が現代の正解。
