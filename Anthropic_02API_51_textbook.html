Text chunking strategies— RAGの精度はchunkingで8割決まる

Anthropic Academy / コース02 Claude with the Anthropic API

① まず結論 — chunkingって何?

長い文書 (例: 100ページのPDF・1万行のWiki) を、意味のある小さな単位 に分割すること。これを chunk (チャンク) という。

なぜ分ける?
  • ① embedding 限界: Voyage AI 等は1チャンクの最大トークン数制限あり
  • ② 検索精度: 1チャンクが大きすぎると「関連箇所」が薄まる
  • ③ コスト: Claude に渡すとき、関係ない部分は無駄なトークン
  • ④ コンテキスト集中: Claude が「該当箇所だけ」読めば正確に答えられる

② 4つの代表的な chunking 戦略

戦略方法適する場面
① 固定サイズ500トークンずつ機械的に切るとりあえず動かしたいPoC
② 文単位 (sentence)句点で区切る短文中心 (Twitter / FAQ)
③ セクション単位Markdown見出し / 章タイトルで分割構造化文書 (本コース ipynb で使用)
④ Semantic chunking文章の意味が変わる境界で動的に分割高精度が必要・コストOK
本コースでの選択: ③ セクション単位。chunk_by_section 関数で Markdown の "\n## " 区切りで分割する。

③ ipynb の実装 — 1行関数

import re

def chunk_by_section(document_text):
    pattern = r"\n## "
    return re.split(pattern, document_text)

たったこれだけ。Markdown の ## セクション見出し ごとに分割する。

本コース ipynb 002 / 003 / 004 全部で同じ関数を使用。RAGの心臓部 (embedder / vector store) を学ぶ前に、まず 正しい単位で切る ことが第一歩。

④ Overlap — 文脈断絶を防ぐテクニック

固定サイズで切ると、文の途中で切れる ことがある:

chunk1: "...重要なのは X である。Y は次の章で..."
chunk2: "...説明する。Y は実は Z と関係..."

これだと chunk2 だけ検索ヒットしても「Yの説明はchunk1にある」がわからない。

対策: chunk と chunk の境界で 50-100トークン重複 させる (overlap=100)。
→ 検索ヒットしたチャンクの前後文脈が確保される。
戦略overlap備考
固定サイズ10-20%推奨 (500トークンなら50-100)標準パターン
セクション単位通常0でOK章は自然な境界
文単位不要1文単位なら原子的

⑤ サイズの目安 — 何トークンで切る?

用途推奨サイズ理由
FAQ / 短い答え100-300トークン1問1答単位
一般的なRAG (推奨)500-1000トークン1パラグラフ〜1セクション
技術文書1000-2000トークン1関数の説明全体
長文小説・論文2000-4000トークン1章単位
目安は500-1000トークン (= 日本語で1000-2000文字 = A4半ページ程度)。
小さすぎる: ヒットしても情報不足 / 大きすぎる: ノイズ多い・コスト高

⑥ 失敗パターン — やってはいけない切り方

NG1: 単語の途中で切る

"Anthropic は AI 企業..." → "Anthropi" + "c は AI 企業..."
→ 単語が切断されると embedding 精度が落ちる。固定サイズなら 最後の改行 or 句点で調整。

NG2: 表・コードブロックを切る

1つの表が複数チャンクに分断されると意味が壊れる。
対策: マークダウンパーサ でブロック単位を認識して、表は分割しない。

NG3: メタデータを捨てる

chunk だけ保存して「どのファイルの何ページ」を忘れる → citation できない。
対策: 各 chunk に {"content": "...", "source_url": "...", "page": 5} でメタデータ同梱。

NG4: 同じ chunk が複数回入る

事前に de-duplication しないと、検索結果が重複だらけになる。
対策: ハッシュで重複検知 + 1つに統合。

⑦ 高度な戦略 — Contextual Retrieval (Anthropic公式)

Anthropic は 2024年に Contextual Retrieval を提唱:

# 通常chunking
chunk = "売上は前年比20%増だった。"
# ↑ どの会社・どの年か不明 → 検索精度低い

# Contextual chunking
contextualized_chunk = """
<document>Anthropic 2025年Q3決算報告</document>
<section>業績概要</section>
売上は前年比20%増だった。
"""
# ↑ Claude に「このchunkは何の文脈か」を1文付け足してもらう
効果: 検索精度が 35%改善 (Anthropic ブログ実測)。
コスト: Claude による前処理 + prompt caching でほぼゼロ。

⑩ 理解度チェック

Q1. なぜ chunking が必要?

① embedding model のトークン制限 ② 検索精度 (関連部分のみ抽出) ③ コスト (Claude に渡す量) ④ Claude のコンテキスト集中 — 4つの理由で必須。

Q2. 本コースで使う chunking 戦略は?

セクション単位 (chunk_by_section)。Markdown の "\n## " 区切りで分割。
理由: report.md が構造化されたマークダウンなので、章境界が自然な意味境界になる。

Q3. overlap (重複) を入れる目的は?

chunk の境界で 文や文脈が切れる のを防ぐ。500トークンチャンクなら50-100トークン程度を次のchunkにも含める。

Q4. Contextual Retrieval って何?

Anthropic 提唱の高度なchunking戦略。各chunkに「これは何の文書のどのセクションか」を1文付け足してから embedding する。検索精度が35%改善。
